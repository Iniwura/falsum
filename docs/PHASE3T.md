# FALSUM Phase 3T — Understandable guided security review demo

**User feedback:** The earlier Phase 3S editorial site looked impressive but did not answer the core question: **what does FALSUM do?** A generic before/after code dashboard is not an understandable demonstration of an evaluator-track entry.

## New first-time visitor journey

**A clear question:** “Which security review should pass?”

1. **Read a fictional situation** in plain English. The first scenario introduces a signed-in user who requests money from someone else's fictional account; the next two cover unauthenticated agent callbacks and repeated relayer credits.
2. **Choose the stronger of two public sample reviews.** These statements were written for this demo and are **not the output of a live trained AI model or actual confidential Anjoman preference pairs**.
3. **Get immediate feedback.** FALSUM explains why a superficially confident answer misses the key risk, or why an evidence-seeking answer is stronger.
4. **Reveal an actual local Python test.** The existing Phase 3Q function was executed at build time. Visitors see both observed before/after outcomes, the legitimate positive control, and the real source implementations and SHA256 hashes behind an optional developer disclosure.
5. **Complete all three cases**, see a score out of three, and restart without any login, wallet, API key or network call.

The site **does not score an AI model live**, claim actual external audits, or expose hidden evaluation data. Its goal is to *explain the difference between fluent and evidence-grounded security reviews* while showing real, reproducible fictional behavior tests. The user's separate **20 eligible** `SECURITY_REVIEW_GENERAL` Anjoman contribution and public bounty claim remain unchanged.

## Visual and usability changes

- Clear, high-contrast near-black and blue design, closer to a premium interactive security application than a static portfolio.
- The interaction is near the top of the page. Simple progress steps make the action obvious.
- Three short realistic stories and their fake identities/event records replace dense unmotivated code.
- Two large clickable review options with instant correctness and explanation. Wrong answers still reveal evidence; no failure dead-end.
- Clear “Reveal the actual test,” then “Next case,” followed by the result score and restart.
- Advanced source code is collapsed by default so visitors **do not need to understand Python** to understand the finding.
- Responsive 320px/390px/mobile and desktop breakpoints; keyboard-focusable buttons; `aria-pressed`, status announcements and reduced motion.
- No external font, CSS, JS, image, analytics or API dependencies.

## Truthful technical boundaries

- **Real:** Three existing Python pairs genuinely execute. The code snippets and checksums displayed in the proof were taken from the same source functions used in those executions. An honest local test blocked all three fictional unsafe actions after patches while preserving all three controls.
- **Written public demonstration:** Each correct and incorrect review is an original, constructed sample (not generated by a model). We do not certify subjective review accuracy on independent production data.
- **Separate network contribution:** 20 evaluation preference pairs appear `Eligible` in the submitting Anjoman account. Their actual hidden questions/answers, account credentials and row hashes do not appear in the public demo.
- **Not claimed:** A registered working Telegraph evaluator model, independent security expert approval, real funds or customer security incidents, actual third-party mission integration, maintainer award confirmation or final Season II hackathon submission.

## Technical validation

The original real Python evidence suite, strict integrity/fingerprint checks, private-data restrictions, official Telegraph diagnostic gate and all tests on Python 3.11–3.13 are preserved. [Phase 3T browser tests](../tests/browser/phase3t_judge_flow.cjs) also exercise:

- Incorrect case-one answer and immediate explanation.
- Before/after proof outcome, source code and SHA256.
- Correct answer on case two and three and final 2/3 score.
- Restart resets all answers and disables premature proof disclosure.
- Keyboard choice, touch reveal, narrow mobile layout (390px and 320px), zero console errors.
- Screenshots of desktop hero/proof and mobile hero/proof retained as GitHub CI artifacts.

The [dedicated Phase 3T workflow](../.github/workflows/phase3t-judge-demo.yml) must be green before merge. The public Vercel site must be checked **after deployment** for actual HTTP 200, source commit, user flow and screenshot layout. Do not call browser QA complete from static tests alone.

## Reproduce

```bash
git clone https://github.com/Iniwura/falsum.git
cd falsum
PYTHONPATH=src python3 -m falsum.phase3q_mission_lab --out-dir public
python3 -m http.server --directory public 8765
```

Open `http://localhost:8765`. Select one review in each of the three cases, reveal the evidence and continue to the next. Exact captured runtime results are in `public/ACTUAL-SYNTHETIC-RUNTIME-PROOF.json`.

**Why this is a better judge story:** “The AI sounded confident. Here is the missing context. This is what the code did. This is what the safe review should have said.” That story connects a genuinely eligible evaluation-material contribution to a transparent and useful measurement problem.
